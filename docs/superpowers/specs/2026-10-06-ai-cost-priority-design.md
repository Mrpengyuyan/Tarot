# 在线解读成本优先设计

- 日期：2026-10-06
- 状态：待用户审阅
- 范围：`Server/` 的真实 AI 解读和 Unity 在线结果页；离线牌义不调用模型

## 1. 目的与已确认的取舍

玩家人数不多，但在线解读使用项目作者自己的 API Key。目标是让后台不会在玩家不知情时重复发出可能计费的请求，同时保持失败后可以由玩家主动恢复。用户已接受：超时后不自动重试；玩家可以决定是否再试一次，而第二次也可能产生费用。

本设计把“每条预测最多一次自动发出的上游 HTTP 请求，加一次玩家明确触发的 HTTP 请求”作为可测试的边界。它限制请求次数，不承诺模型服务商的实际账单精确等于本地估算，也不承诺一次发出就一定有可用结果。

## 2. 当前实现与问题

- `Server/app/services/coze_service.py` 目前可能依次尝试配置地址与备用地址、按 `AI_MAX_RETRIES` 重试，并切换到 reasoner。示例配置开启了超时重试和 reasoner；预算允许时，一局可能发出多次 HTTP 请求。
- `Server/app/services/budget_store.py` 已对每次请求原子预留日/月估算额度。超时后保留预留额是保守的成本保护，但会令可用额度早于实际账单耗尽。`AI_REQUEST_SOFT_CAP_USD` 在收到用量后检查，不是请求前的硬上限。
- `Server/app/api/v1/endpoints/records.py` 的生成权过期时间为 300 秒。旧任务结果已由 claim token 防止覆盖新结果，但过期后重新抢占仍可能产生另一笔上游请求。
- `UnityClient/TarotUnity/Assets/Scripts/Network/InterpretationPoller.cs` 在启动 POST 的响应丢失时可能自动重发 POST；其“重新解读”按钮则是明确的玩家操作。两者必须分开处理。
- 普通/访客账号每天 3 局的限制不是全局成本上限；新建访客账号可以绕开每账号次数。真正的总成本保护仍是数据库预算及服务商账户控制。

## 3. 选定策略

### 3.1 一次任务只发一个上游请求

在线解读路径固定使用配置的单一 chat 地址和模型。对已经可能发送的请求，不自动尝试备用地址、重定向、超时重试、5xx 重试或 reasoner 回退；响应格式错误也不以第二次请求修复。明确的配置错误、鉴权错误直接失败。请求必须有总墙钟时间限制，不能靠每个网络阶段各自的超时无限延长。

这个限制覆盖同步 `POST /records/{id}/interpret?force_ai=true` 和异步 `POST /records/{id}/interpret/async`，不能由同步接口绕过。现有 mock/离线逻辑不计入上游请求次数。健康检查不能绕过相同的预算预留；任何会发出付费请求的独立管理功能不在本次玩家解读流程内，应单独审核。

### 3.2 初次启动与人工重试分离

首次启动仍用 `POST /records/{id}/interpret/async`。它是幂等的：对于已有尝试的记录只返回当前状态或明确错误，不会再次创建付费任务。新增 `POST /records/{id}/interpret/retry`，仅在所属玩家主动操作、第一轮没有结果且状态已终止或未知时可用；同一预测最多接受一次已发送请求后的人工重试。同步 AI 接口仅能创建第一轮请求；若第一轮已用且没有结果，它返回“需人工重试”，不能充当第二或第三条入口。

若第一次请求仍标记为运行中，不允许人工重试。若已保存解读，所有入口返回原结果且不再调用模型。预算拒绝发生在网络发送之前时，不消耗“可能计费的请求”名额，但返回预算不可用状态，不在后台自动循环尝试。已发送后的超时、连接中断、5xx 或进程退出一律视为费用不确定；不自动重发。

### 3.3 持久状态与并发边界

在 `predictions` 上增加独立于现有 `status` 的解读请求状态、可能已发送的请求次数、开始发送时间和最后失败类别，使用 Alembic `0005` 迁移。状态为 `not_started`、`scheduled`、`sending`、`retry_required`、`budget_blocked`、`completed`、`exhausted`；当前 claim token 继续使用已有的 `interpretation_started_at`。`Prediction.status=PROCESSING` 也可能只表示已抽牌，不能单靠它判断 AI 是否发出。已有的 `interpretation_attempts` 仍记录任务抢占次数，不作为付费请求上限。

迁移已有记录时，有解读的标记为 `completed`；已有生成尝试但无解读的记录按“可能已发送”保守计数，最多记两次。计一次的转为 `retry_required`，计两次及以上的转为 `exhausted`，不会重新自动启动；没有生成尝试的转为 `not_started`。部署迁移前应停止旧后端写入，避免旧 worker 与新状态规则同时运行。

在真正调用模型前，先用现有预算存储预留额度，再用数据库原子条件更新占用一个请求名额并持久化 `sending`，最后才允许唯一一次 HTTP POST。若更新失败，应释放尚未使用的预算预留，不发送请求。同一 claim 至多成功占用一次。完成时以 claim token 更新结果或终态。进程若在持久化 `sending` 后、实际发送前退出，该名额也按“可能已发送”保守处理；这是避免崩溃后自动重复调用所需的可用性取舍。预算拒绝发生在 `sending` 之前，不占用请求名额。预算预留后、请求标记前的进程崩溃可能保留一笔未使用的预留额；它只能降低可用额度，不能产生额外付费请求。

旧的 300 秒过期规则不再自动重启付费解读。单次网络调用的墙钟上限为 90 秒；`sending` 超过 120 秒仍无结果时，查询状态的路径通过条件更新将其转为 `retry_required` 或 `exhausted`，但不发新请求。`scheduled` 超过 300 秒且仍未开始发送时，同样转为 `retry_required`，仅由玩家手动恢复。旧 worker 即使后来返回，也不能覆盖新 claim 的状态或结果。对迁移时已经处于 `PROCESSING` 且无解读的记录，按费用不确定处理，不自动重新发送。

数据库中保留生成权和次数作为唯一并发判定；进程内锁仅可用于性能，不可作为成本边界。正常运行或重启后，客户端重复 POST、多个 worker 并发和双击重试都不能多占一次名额。

## 4. 接口与 Unity 行为

`GET /records/{id}` 增加一个解读运行摘要，至少包含 `state`、`can_retry`、`requests_started`、`max_requests`，以及预算阻止时的下次可尝试时间。`can_retry` 只有在状态允许、名额未耗尽且预算窗口允许时为真；预算不足时玩家可等窗口恢复后再次主动操作，但不会自动排队。这些字段只对记录所有者返回，不暴露 API Key、供应商错误正文、完整提示词或预算细节。旧字段和已有解读结构保持兼容。

Unity 的 `InterpretationPoller` 首次只发送一次启动 POST。即使该 POST 的响应丢失，也只查询 `GET /records/{id}`，不自动再 POST。轮询只读取状态，不创建任务。结果页在 `sending` 时显示等待；在 `retry_required` 时显示“这次在线解读未能确认结果，再试一次可能再次调用 AI”，并提供“再试一次”与“查看离线解读”。按钮只调用新的人工重试接口一次；重复点击被禁用，服务端仍负责最终防重。额度不足或两次名额用完时不显示可用的付费重试按钮，而保留离线解读。预算窗口恢复后，玩家可以再次主动点击，但预算拒绝期间不在后台排队或自动启动。

客户端 330 秒等待期限届满而服务端仍报告 `sending` 时，只停止当前画面的轮询并提示“仍在处理中，可稍后查看或使用离线解读”，不得擅自把它改成可重试。重新进入结果页先读服务端状态。超时后若服务端已判定 `retry_required`，才允许人工重试。

## 5. 错误处理、预算与发布

- 上游返回成功并提供可用结果：保存解读、结算实际用量，状态为 `completed`。
- 明确在发送前失败，包括未配置 Key、预算不足或无效参数：不发上游请求；显示不可用原因，不自动重试。
- 发送后超时、网络错误、上游 5xx、响应损坏或进程中断：保留保守预算预留，状态最终为 `retry_required` 或 `exhausted`；日志记录请求 ID 和失败类别，不记录密钥及完整牌面问题。
- 每次请求都先走现有数据库日/月预算预留。估算值与实际供应商账单可能不同，因此上线前还要核对实际环境配置，并在服务商侧设置可用的账户额度或告警；不能把应用内估算额度称为绝对账单封顶。
- 首次发布先运行迁移、部署后端，再部署 Unity 客户端；旧客户端重复调用初次启动接口也不得触发第二笔请求。无真实 API Key 的自动化测试不能消耗费用。

## 6. 验收条件

1. 一次首次启动至多触发一个上游 HTTP POST；任何自动重试、备用地址、重定向或备用模型都不能新增请求。
2. 首次请求超时、响应丢失、任务崩溃或超过 300 秒后，重复初次启动 POST 与普通轮询都不再发付费请求。
3. 玩家明确点击后，人工重试最多发一个额外上游 HTTP POST；双击、并发客户端和同步接口无法突破同一预测最多两个可能计费请求的边界。
4. 预算拒绝发生在网络发送前时，上游请求次数不增加；多进程并发仍不能突破数据库预算预留限制。
5. 旧任务的迟到成功或失败不能覆盖新任务的结果和状态。Unity 能分别显示等待、费用不确定、额度不足、次数用尽、成功和离线结果。
6. 后端回归测试及 Unity EditMode/PlayMode 的相关测试通过；用模拟 HTTP 统计调用次数，不在 CI 或单元测试中调用真实付费 API。

## 7. 非目标与剩余风险

本期不引入 Redis/Celery 等持久任务队列，不自动查询模型服务商账单，也不保证“恰好计费一次”。发送请求后即使客户端没有收到响应，服务商仍可能完成并收费；玩家选择人工重试时可能再次收费。持久化 `sending` 后进程退出也可能让一次未真正发送的请求占用名额。这个保守偏差是用户已选择的“成本优先”策略，换取不在后台悄悄增加请求。

只改配置无法阻止代码中的备用地址尝试，也无法在进程重启后区分“还没发送”和“可能已发送”；完整队列能改善任务恢复，但不能单独保证外部服务恰好处理一次，还增加部署与运维负担。因此本期选用数据库状态与显式人工重试，不引入新的运行服务。
